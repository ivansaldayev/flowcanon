# workflow-solo (regeneration run, the team lead runs the script)

**When to use:** places — one home entry = one place = the subject of one decision — fixed or built by regeneration through the `Workflow` tool: each round a fresh executor writes the place from scratch, and a review finding rewrites the TASK, never patches the code. You run the script yourself, one place at a time, and handle its stops; the place is investigated INSIDE the run by an intake analyst. The owner gave no signal to hear the investigation before code, and the work needs no parallel trees.

**Participants:** the team lead (runner). Inside the run, disposable agents per call: sage (intake analyst, rounds analyst — their roles in `workflow/roles.md`), developer (executor), reviewer ×N (lenses, parallel), review-lead (consolidation — the gate). The script is the lead of these agents: pool, models and rounds live in the script and the run descriptor, not in an agent file (the script-driven exception in [../flowmaker.md](../flowmaker.md)). Author ≠ gatekeeper holds: the executor never judges, review-lead never writes code. About eleven agents per round, up to the ceiling — beyond the tool's default size guideline by design.

## Order

1. Establish two absolute paths yourself — the script has no filesystem: `root` — the superproject root (the directory holding the submodules); `skillDir` — the `workflow/` directory next to this file, at the path you read this flow from. Never `cd` for either: a changed cwd breaks the tool silently (`workflow/tool.md`).
2. Write the run descriptor once per run — every field is named in `workflow/run.example.json`; required here: `name`, `repos`, `prefix`, `sources`. It carries no absolute paths, so one descriptor serves every clone. Read it and pass the object as `args.run`.
3. Per place, one at a time, with the working tree under `root` clean of your own edits to the place's files: `Workflow({ scriptPath: '<skillDir>/solo.js', args: { root, skillDir, run, place, slug, home } })` — `place` is the place's name as the sources call it; `home` is the place's home entry — where the place is stated and the decisions on it are recorded — by the address the project's records give it (a root-relative file path, when entries are files): the intake analyst reads it whole itself, you retell nothing; `slug` is a short id unique within the run and valid as a file name: the task and the findings registry are `<prefix><slug>-task.md` and `<prefix><slug>-findings.md`, where `<prefix>` is the descriptor's `prefix`. Report the launch only once the tool returned a runId — «launching» without one is an intention, not a fact.
4. Read the result. Verdicts: `APPROVE`; a stop `A` (executor blocked) or `B` (review-lead blocked) with `awaitingOwner`; `ESCALATE` with `ownerBrief` and a `reason` — `contradiction` (the rounds analyst: rounds contradict each other, a decision class no norm or owner decision covers, or a cure beyond the place), `systemic` (the intake judged the radius systemic), `unmeasurable` (the intake needed a consumer in a repository not checked out under `root`); `RETURN` with reason `MAX_ROUNDS`. When review-lead disputes the task's premise, a second intake runs: if it writes a new task, the place is rolled back whole and the rounds restart from one, and nothing surfaces; if it escalates, the run stops with the round's edits still in the tree and the reason carries a `-on-premise` suffix. Resume it like any escalation (step 5): a third intake runs with the owner's answer and either writes the task — then the rollback and the restart follow — or escalates again, and the run stops again. Beside the verdict the result carries findings that leave the run: `questions`, `execQuestions` and `unresolved` (a behaviour dispute review-lead could not settle) go to the owner with the verdict; `normFixes` (review-lead) and, on an escalation, `normCandidates` (the analyst) are norm candidates — check each premise, report each to the owner in one line and record it in `CLAUDE_CANDIDATES.md` next to the `CLAUDE.md` it is meant for, never in the norm itself; `recordItems` / `recordCandidates` become entries of their own on the owner's word.
5. A stop or an ESCALATE is a BLOCKED of the run — handle it as any BLOCKED (teamlead.md, Blocker triage and Vision gaps): answer what the records determine, bring the rest to the owner with `awaitingOwner` / `ownerBrief` verbatim. Record the owner's answer as a dated note in the home entry BEFORE resuming — the agents inside verify it from the primary source. Resume with the SAME call plus `resumeFromRunId` and `args.ownerAnswer` (the answer verbatim), everything else byte-identical. Stop B has no resume: settle the task with the owner and launch anew. A `MAX_ROUNDS` return goes to the owner with the registry path; continuing is a new launch with `maxRounds` raised in the descriptor — a ceiling return has no resume. Every new launch — after stop B, after `MAX_ROUNDS` (the analyst rolled back the files with findings, the rest keep the last round's code), or after a result with `error` in place of a verdict that carries `files` (a run stopped on a bad agent answer, the round's edits still in the tree) — starts with rolling the place back whole, per repo, paths from the repo's root: `git -C <root>/<repo> checkout HEAD -- <tracked paths>` for the result's `files` minus `newFiles`, `git -C <root>/<repo> clean -f -- <new paths>` for `newFiles`, each command only when its list is not empty: a new file in `checkout HEAD` aborts the whole command on a pathspec error, and `clean -f --` with no paths removes every untracked file of the repo.
6. After APPROVE: re-measure the delta with your own hand — `git -C <root>/<repo> diff HEAD --numstat -- <paths>`, one command per repo, `<paths>` being the result's `files` of that repo with the repo segment stripped (git takes paths from the repo's root, and a root-relative path yields an empty, exit-0 diff), and `wc -l` over the result's `newFiles`, which `git diff HEAD` does not see — no verdict is accepted by a report's numbers. Commit only on the owner's word.
7. Terminal state: APPROVE with the delta verified — ready, waiting for the owner.

Recon mode — `Workflow({ scriptPath: '<skillDir>/solo.js', args: { root, skillDir, run: <run with prefix = <prefix>recon->, places: [{ place, slug, home? }, …] } })` — raises the intake analysts of all listed places at once and touches no code. Each result row carries `action` (`TASK_READY`, or `ESCALATE` with `ownerBrief` — a systemic radius, or a repository not checked out under `root`; to the owner), `files`, `radius` (the consumer measurement) and `behaviourChange` (whether callers observe a change). The tasks it writes under the recon prefix are drafts for grouping only — the run's own intake starts from nothing and writes the task under `<prefix>` — so remove them once the places are grouped: `rm <root>/<prefix>recon-*-task.md`. Use it to decide how to group places before any code is written.

## Gates

The gate is review-lead's APPROVE over the executor's report and the lenses; RETURN is lawful on integrity alone. One difference from the gate semantics of [../teammate.md](../teammate.md): a finding never returns to the code — it returns to the TASK as a positive prescription with its source; the files with findings are rolled back and rewritten (all of them when every file has findings); the round ceiling comes from the descriptor. Executor rules — `workflow/common.md`; in-run roles — `workflow/roles.md`.

## Watch-outs

- Do not edit owner decisions or the sources under a live run without saying so: an agent inside cannot learn of the edit, and a quote in the task outweighs the primary source.
- An agent's report is a claim to verify, not a fact — norm candidates included: check each premise before bringing it to the owner.
- `resumeFromRunId` lives only in the session that launched the run — keep the session until the place closes; a run left behind by an ended session can only be launched anew.
