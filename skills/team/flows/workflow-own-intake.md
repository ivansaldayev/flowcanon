# workflow-own-intake (regeneration run, the team lead investigates)

**When to use:** a place — one home entry = the subject of one decision — fixed or built by regeneration through the `Workflow` tool, when the owner wants to hear the investigation and settle its questions BEFORE any code is written. You investigate the place yourself, present the vision to the owner, write the task, and only then run the script; the run has no intake of its own. One place at a time, in your session.

**Participants:** the team lead (investigator, task author, runner); the owner (decisions before the run); inside the run, disposable agents per call: developer (executor), reviewer ×N (lenses, parallel), review-lead (consolidation — the gate), sage (rounds analyst). The script is the lead of the in-run agents: pool, models and rounds live in it and in the descriptor, not in an agent file (the script-driven exception in [../flowmaker.md](../flowmaker.md)). Author ≠ gatekeeper holds: you write the task, never the code; the executor never judges; review-lead judges the code, never writes it. About eleven agents per round, up to the ceiling — beyond the tool's default size guideline by design.

## Order

1. Establish `root` (the superproject root) and `skillDir` (the `workflow/` directory next to this file, at the path you read this flow from) — the script has no filesystem. Never `cd` for either: a changed cwd breaks the tool silently (`workflow/tool.md`). Write the run descriptor once (`workflow/run.example.json`; required: `name`, `repos`, `prefix`; no `sources` — you are the intake). No absolute paths in it. Read it and pass the object as `args.run`.
2. Investigate the place per `workflow/roles.md`, sections «Place and edit radius» and «Intake analyst», in the analyst's seat; where the section names the descriptor's sources, yours are: the home entry (`home` in the call — where the place is stated and the decisions on it are recorded) read whole, with every dated note, the class's home found by your own search — every candidate read whole, not summaries — the code by grep, the project docs when a screen is involved. Answer the three questions — what is actually wrong, local or systemic by radius, what design requires — and declare the file list, complete and minimal, new files named apart. Consumers are measured only in repositories checked out under `root`; assembling the tree is yours — `git -C <root> submodule update --init <repo>` before measuring. Read the primary sources yourself (teammate.md, Fact discipline); a sub-agent may look things up, its report is a claim.
3. Present the vision to the owner in the chat: the defect restated, the radius verdict with its measurement, the files, what design requires, every open question with your recommended answer. A systemic radius is presented as such — whether the place is taken wider or split is the owner's decision. Record the owner's decisions as a dated note in the home entry, verbatim — the executor and the review verify quotes from there. A norm candidate met on the way is reported in one line and goes to `CLAUDE_CANDIDATES.md` next to the `CLAUDE.md` it is meant for, never into the norm itself.
4. Write the task `<prefix><slug>-task.md` per the «Intake analyst» section — `<prefix>` is the descriptor's `prefix`, `slug` a short id unique within the run and valid as a file name; the findings registry will be `<prefix><slug>-findings.md`. Every prescription carries its source: the owner's quote with its address, or «the team lead's reading, not an owner decision, open to dispute».
5. Run, with the working tree under `root` clean of your own edits to the place's files: `Workflow({ scriptPath: '<skillDir>/own-intake.js', args: { root, skillDir, run, place, slug, home, files, newFiles?, kept? } })` — `place` the place's name as the home entry and the task call it, `home` the home entry by the address the project's records give it (a root-relative file path, when entries are files), `files` your declared list, root-relative, `newFiles` its subset absent from HEAD, `kept` its subset left in the tree from a previous launch (step 6). Report the launch only once the tool returned a runId.
6. Read the result. Verdicts: `APPROVE`; stop `A` / `B` with `awaitingOwner`; `ESCALATE` with `ownerBrief` and the reason `contradiction` — the rounds analyst: rounds contradict each other, a decision class no norm or owner decision covers, or a cure beyond the place; the only reason here, since the run has no intake; `RETURN` (`MAX_ROUNDS`); `PREMISE` — review-lead disputed the task's premise; with no intake inside the run to rewrite the task, the run stops and the place is rolled back whole. Beside the verdict the result carries findings that leave the run: `questions`, `execQuestions` and `unresolved` (a behaviour dispute review-lead could not settle) go to the owner with the verdict; `normFixes` (review-lead) and, on an escalation, `normCandidates` (the analyst) are norm candidates — check each premise, report each to the owner in one line and record it in `CLAUDE_CANDIDATES.md` next to the `CLAUDE.md` it is meant for, never in the norm itself; `recordItems` / `recordCandidates` become entries of their own on the owner's word. A stop or an ESCALATE is a BLOCKED of the run — handle it as any BLOCKED (teamlead.md, Blocker triage and Vision gaps): answer what the records determine, bring the rest to the owner verbatim; record the answer as a dated note in the home entry; resume with the SAME call plus `resumeFromRunId` and `args.ownerAnswer`, everything else byte-identical (stop B has no resume: settle the task with the owner and launch anew). A `MAX_ROUNDS` return goes to the owner with the registry path; the analyst rolled back the files with findings and the rest keep their reviewed code, so continuing is a new launch with `maxRounds` raised in the descriptor and the result's `kept` passed as `kept` — a ceiling return has no resume. `PREMISE`: rewrite the task with the owner and launch anew. Any other new launch — after stop B, or after a result with `error` in place of a verdict that carries `files` (a run stopped on a bad agent answer) — starts from a tree that still holds the round's edits: roll back every file of the place except the result's `kept`, when it has one — per repo, paths from the repo's root: `git -C <root>/<repo> checkout HEAD -- <tracked paths>` for `files` minus `newFiles` minus `kept`, `git -C <root>/<repo> clean -f -- <new paths>` for `newFiles` minus `kept`, each command only when its list is not empty: a new file in `checkout HEAD` aborts the whole command on a pathspec error, and `clean -f --` with no paths removes every untracked file of the repo — and pass `kept` as `kept`.
7. After APPROVE: re-measure the delta with your own hand — `git -C <root>/<repo> diff HEAD --numstat -- <paths>`, one command per repo, `<paths>` being your `files` of that repo with the repo segment stripped (git takes paths from the repo's root, and a root-relative path yields an empty, exit-0 diff), and `wc -l` over your `newFiles`, which `git diff HEAD` does not see. Commit only on the owner's word.
8. Terminal state: APPROVE with the delta verified — ready, waiting for the owner.

## Gates

Two gates: the owner's decisions on your vision before the run, and review-lead's APPROVE inside it; RETURN is lawful on integrity alone. A finding never returns to the code — it returns to the TASK as a positive prescription with its source; files with findings are rolled back and rewritten (gate semantics — [../teammate.md](../teammate.md); the regeneration difference — `workflow/roles.md`). Executor rules — `workflow/common.md`.

## Watch-outs

- Do not edit owner decisions or the sources under a live run without saying so.
- `resumeFromRunId` lives only in this session — keep it until the place closes; a run left behind by an ended session can only be launched anew.
