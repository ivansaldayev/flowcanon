# workflow-streams (regeneration runs by teammate streams)

**When to use:** a pool of places — one home entry = one place = the subject of one decision — run in parallel by regeneration through the `Workflow` tool. Two sessions: a planning session recons the whole pool, cuts it into streams and records them; a fresh run session raises one teammate per stream in its own worktree. A stream lives inside ONE submodule; a place whose files spill beyond one submodule is out of scope. Work that touches several submodules (e.g. a server and a client) makes the trees much harder to build — choosing this flow for such work is justified to the owner, never assumed.

**Participants:** the team lead (planning: recon and slicing; run: streams and their state, nothing below); one `sage` teammate per stream (the runner); inside each run, disposable agents per call: sage (intake analyst, rounds analyst), developer (executor), reviewer ×N (lenses), review-lead (the gate). The script is the lead of the in-run agents: pool, models and rounds live in it and in the descriptor, not in an agent file (the script-driven exception in [../flowmaker.md](../flowmaker.md)). Author ≠ gatekeeper holds: the executor never judges, review-lead never writes code. About eleven agents per round per stream, up to the ceiling — beyond the tool's default size guideline by design. Every place is investigated twice by design: by the recon with every submodule present, and again by the intake inside the stream's tree.

## Planning session — the team lead

1. Establish `root` (the superproject root) and `skillDir` (the `workflow/` directory next to this file, at the path you read this flow from) — the script has no filesystem. Never `cd` for either: a changed cwd breaks the tool silently (`workflow/tool.md`). Write the run descriptor (fields — `workflow/run.example.json`; required: `name`, `repos`, `prefix`, `sources`; no absolute paths — every tree reuses it), save it to `<root>/<prefix>run.json`, `<prefix>` being its `prefix`, and pass it as the object `run`. The owner names the run, and you write `name` as a kebab-case token valid as a file name, because it is also the WAL's name; below, `<name>` is that name and `<recon>` is `<prefix>recon-`.
2. Recon over the whole pool — the owner's list of places, slugs assigned by you: `Workflow({ scriptPath: '<skillDir>/streams.js', args: { root, skillDir, run: <run with prefix = <recon>>, places: [{ place, slug, home? }, …] } })` — intake analysts only, no code. `place` is the place's name as the sources call it, `home` the place's home entry — where the place is stated and the decisions on it are recorded, by the address the project's records give it (a root-relative file path, when entries are files) — read as the primary source, `slug` a short id unique within the run and valid as a file name. Write the tool's returned object to `<root>/<recon>record.json` with the Write tool — the recon record; its `places` rows carry `action` (`TASK_READY`, or `ESCALATE` with `ownerBrief` — a systemic radius, or a repository not checked out under `root`; to the owner), `files`, `radius` (the consumer measurement) and `behaviourChange` (whether callers observe a change). The tasks the recon wrote under `<recon>` are drafts: the stream's own intake writes the task anew.
3. Cut the streams by the record's `files`: no file in two streams, one submodule per stream (several streams may share a submodule). A place overlapping two streams merges them into one; a place whose `files` span two submodules is out of scope — to the owner, together with what the recon escalated.
4. Record in the WAL `<name>` (skill `wal`, `write <name>`): the descriptor path, the recon record path, the justification given to the owner when the streams lie in several submodules, and per stream its submodule and ordered places `{ place, slug, home }`. Remove the drafts: `rm <root>/<recon>*-task.md`. End the session.

## Run session — the team lead

1. Check `echo $TMUX`; empty → BLOCKED to the owner (restart under tmux), spawn nothing. Establish `root` and `skillDir` as above; read the WAL `<name>` (skill `wal`, `read <name>`) — the owner gives the name at the start; without it, `list` shows the active WALs.
2. Per stream: a worktree of the superproject (`git -C <root> worktree add <tree> -b <branch>`) with only the stream's submodule initialized (`git -C <tree> submodule update --init <repo>`) and a branch inside it (`git -C <tree>/<repo> checkout -b <branch>`): an initialized submodule sits on a detached HEAD, and a commit there would belong to no branch — check that `git -C <tree>/<repo> status` reports the branch. This sequence is written from git semantics, not from a run under this flow.
3. Per stream, spawn ONE `sage` teammate with the standard first-prompt line (teamlead.md, Teammate Instructions), this flow's path, the tree as its `root`, `skillDir`, the descriptor path and its ordered places.
4. Keep ONE table: stream → current place, state (running / awaiting the owner / approved / escalated / ceiling), runId. That is your whole picture; do not read tasks, registries or verdicts — the volume would fill your context. A norm candidate a runner hands you with the owner's word you record under the main `root` in `CLAUDE_CANDIDATES.md` next to the `CLAUDE.md` it is meant for, never in the norm itself. A teammate's «stopped, awaiting the owner» goes to the owner as one line with the teammate's name: the owner answers in the teammate's own chat, not through you. Teammates' one-line results update the table; report it to the owner on request and at the end.
5. Terminal state: every stream reports its last place APPROVE with the delta verified, the code committed in the submodule's branch and the pointer in the tree's branch — ready, waiting for the owner (merging is the owner's).

## Run session — the runner teammate

1. Read this flow and `workflow/tool.md`; `root`, `skillDir`, the descriptor path and the places came in your spawn prompt — read the descriptor yourself and pass it as the object `run`. Verify `Workflow` is among your tools, else BLOCKED to the team lead.
2. Per place, in order, with the working tree under `root` clean of your own edits to the place's files: `Workflow({ scriptPath: '<skillDir>/streams.js', args: { root, skillDir, run, place, slug, home } })`; report the runId to the team lead in one line.
3. Verdicts: `APPROVE`; stop `A` / `B` with `awaitingOwner`; `ESCALATE` with `ownerBrief` and a `reason` — `contradiction` (the rounds analyst: rounds contradict each other, a decision class no norm or owner decision covers, or a cure beyond the place), `systemic` (the tree's intake judged the radius systemic), `unmeasurable` (the intake needed a consumer in a submodule this tree lacks; the owner usually answers from the recon record); `RETURN` (`MAX_ROUNDS`). When review-lead disputes the task's premise, a second intake runs: if it writes a new task, the place is rolled back whole and the rounds restart from one, and nothing surfaces; if it escalates, the run stops with the round's edits still in the tree and the reason carries a `-on-premise` suffix. Resume it like any escalation: a third intake runs with the owner's answer and either writes the task — then the rollback and the restart follow — or escalates again, and the run stops again. Beside the verdict the result carries findings that leave the run — `questions`, `execQuestions` and `unresolved` (a behaviour dispute review-lead could not settle), `normFixes` (review-lead) and, on an escalation, `normCandidates` (the rounds analyst) as norm candidates, `recordItems` / `recordCandidates` as candidate entries of their own: post them in your chat under the place, where the owner reads them. A norm candidate the owner accepts you hand to the team lead as one line with the owner's word; the team lead records it under the main `root` — `CLAUDE_CANDIDATES.md` next to the `CLAUDE.md` it is meant for — never in your tree: the worktree does not outlive the stream. On a stop or an ESCALATE: post `awaitingOwner` / `ownerBrief` verbatim in your chat, tell the team lead «stopped, awaiting the owner» in one line, wait for the owner's answer in your chat, record it as a dated note in the home entry, then resume with the SAME call plus `resumeFromRunId` and `args.ownerAnswer` (verbatim), everything else byte-identical. Stop B has no resume: the owner settles the task and you launch anew. `MAX_ROUNDS` — to the owner with the registry path; continuing is a new launch with `maxRounds` raised in the descriptor, a ceiling return has no resume. Every new launch — after stop B, after `MAX_ROUNDS` (the analyst rolled back the files with findings, the rest keep the last round's code), or after a result with `error` in place of a verdict that carries `files` (a run stopped on a bad agent answer, the round's edits still in the tree) — starts with rolling the place back whole, paths from the repo's root: `git -C <root>/<repo> checkout HEAD -- <tracked paths>` for the result's `files` minus `newFiles`, `git -C <root>/<repo> clean -f -- <new paths>` for `newFiles`, each command only when its list is not empty: a new file in `checkout HEAD` aborts the whole command on a pathspec error, and `clean -f --` with no paths removes every untracked file of the repo.
4. After APPROVE: re-measure the delta with your own hand — `git -C <root>/<repo> diff HEAD --numstat -- <paths>`, `<paths>` being the result's `files` with the repo segment stripped (git takes paths from the repo's root, and a root-relative path yields an empty, exit-0 diff), and `wc -l` over the result's `newFiles`, which `git diff HEAD` does not see; commit the code in the submodule's branch, then the submodule pointer in the tree's branch, no push — a standing rule of this flow for teammate runners, which overrides a default no-commit rule of the project's norms; report one line to the team lead: place, verdict, rounds, delta, commits.
5. Next place. When the list is done — a final one-line report; stay alive: the lead may assign more, and `resumeFromRunId` lives in your session only.

## Gates

Review-lead's APPROVE inside each run is the gate; a finding returns to the TASK, files with findings are rolled back and rewritten (gate semantics — [../teammate.md](../teammate.md); the regeneration difference — `workflow/roles.md`). The team lead adds no gate of its own.

## Watch-outs

- Two tiers REQUIRE tmux — outside it the runner has no `Workflow` and the flow silently degrades to nothing.
- A shared file between two trees is a merge conflict waiting for the owner — slice by files (planning step 3).
- A runner never edits owner decisions or the sources under its live run without saying so — a quote in the task outweighs the primary source.
