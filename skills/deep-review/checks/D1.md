# D1 — Decomposition Bug-Class Catalog

Use when reviewing a feature set cut from an epic (decomposition review). Cumulative catalog: a class enters it when a review finds the bug in an artifact that had already passed — so a clean terminal elsewhere is no evidence of absence. Run EVERY class against EVERY feature of the set. When a run's review finds a decomposition bug of a class not listed here, append it after the run (one entry: trigger + what fails).

1. **Identifier baked into token/session changes.** A feature lets the user change an identifier (login, phone, email…) that is embedded in the token/session or other long-lived state, without handling the token/session consequence. Typical: the change surface is specified in full, the session silently breaks after it.
2. **Result delivery misses a user cohort.** A result (a review outcome, an approval decision…) is delivered only along the main flow's path; other cohorts that can reach the same pending state through a different entry point never receive it.
3. **Decision race / re-submission.** Approve/reject racing a repeat submission (or an edit) of the same subject — no rule for which wins, no state guard.
4. **Cross-epic obligation onto a dead or nonexistent target.** An obligation is deferred to an epic that is Canceled or does not exist — the work silently vanishes. The author-side rule (check status at transfer) is in the epic-features flow; this check is the reviewer's side of it.
5. **Missing screen states under a build-absent-states policy.** rejected / empty / error states of a screen are owned by no feature while the project's policy says absent states are built, not skipped.
6. **Reuse-context precondition violation.** A feature reuses a screen/endpoint whose safe behavior depends on a precondition true in its ORIGIN context but false in the new context, so the reuse silently misbehaves (data loss / wrong default). Typical: a save that replaces the whole array is safe on a screen that always opens empty; reused on a screen where data already exists, it wipes that data unless a preload is mandatory. A decomposition that reuses without restoring the precondition (preload current + always send the full set) is flagged.
7. **Server-written value read as a client-local marker.** A feature pins or changes a server-side value of a field the client also uses as its own bookkeeping marker (e.g. an offline queue's «not yet sent» state): once the server value reaches the client, the client misreads it and repeats its action — duplicate submissions / a resend loop. Check the READ side of the field: enumerate the client consumers of every touched value (sync and cache paths above all) and require the body to separate client-only markers from server states. Kin of class 8 — both are incomplete inventories of the paths interacting with an entity. Kin: a queued operation whose error is never made terminal retries forever.
8. **Single-path gate bypassed by batch/generic mutation paths.** A feature installs a gate/invariant on the one-at-a-time operation (single-item form, dedicated edit endpoint) while the same mutation stays reachable via batch, generic-PATCH, admin or import paths that skip the gate — the invariant holds only on paper. Check the WRITE side of the entity: enumerate ALL its write paths and require an explicit disposition for each (gate extended / path forbidden / owner-approved exception). Kin of class 7. Typical: a validation gate on the single-item endpoint bypassed by the bulk endpoint of the same operation; a generic admin PATCH landing status changes past a review step; an admin path skipping a lock check that every client path enforces.
