# C4 — Linter Gap

The project's linter runs before review and its findings are not yours (Noise Filter). Your territory is what the linter was told not to check.

1. Find the linter: the lint/check scripts in the package manifest and the linter config file(s), including any shared config they extend. No linter → report that and stop; lint-class findings then fall to the other checks.
2. List the rules switched off in the effective config — explicit `off` levels and overrides, in every config layer that applies to the changed files.
3. Run the switched-off rules on the changed files. If the linter can run a single rule regardless of config (a rule-selection flag such as `--only` or `--rule`), use it — enumeration by the tool, judgment by you. Otherwise check them by hand.
4. Triage. A rule is usually off because it is noisy; report only the instances where the rule's concern is real on a reachable path — a non-null assertion where the value can be null, an index-as-key on a list that reorders or deletes, a missing effect dependency that reads a stale value, a map callback that returns nothing and so renders nothing. A rule that is off for style (formatting, naming, import protocol) is not a finding.

Do not invent rules beyond the config. Do not re-report what the enabled rules already catch.
