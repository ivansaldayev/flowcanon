# C7 — Trust Boundaries & Data Exposure

- Inputs crossing a trust boundary (user input, client→server requests, external services) are validated before use — through the project's validation layer, before the value reaches logic or storage.
- Authorization beyond authentication: every operation verifies the actor may act on the target object, not just that the actor is logged in — the token's subject against the target's owner field.
- Sensitive data (credentials, tokens, secrets, personal data) does not leak into responses, logs, error messages, URLs, or persisted artifacts — unencrypted client-side storage included.
- Errors returned to the caller do not expose internals (stack traces, queries, paths).

Establish the project's mechanisms yourself before judging — read them, do not assume:

- **Auth**: the token issuing and verifying code and the middleware guarding each route group. Where several token kinds or audiences exist (user vs admin, app vs web), find what actually separates them: a shared signing key means the signature check does not — only the resolve step (which store the subject is looked up in) does. Then the right guard must sit on the right route group, and no guard may be assumed to reject a foreign token cryptographically.
- **Sensitive fields**: from the schemas and config — credential fields, token and key material, the personal data the product handles. Check the response-shaping code strips them (a derived boolean in place of the field, never the field).
- **Shared client**: where requests are meant to go through a shared client that injects auth, a raw request bypassing it loses that injection — a trust finding, not a style one.
- **Rate limiting**: where sensitive endpoints (auth, email, password reset) are rate-limited, a new sensitive endpoint follows suit.
- **Client-side guards are not authorization**: a protected page or action on a client must be enforced by the server route as well.
